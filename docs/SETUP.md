# Owner setup and deployment

These steps have been prepared, not executed against your accounts. Use a staging project first. You can do all routine content work in the dashboard once setup and acceptance testing are complete.

## 1. Your accounts

Use your own GitHub repository, Supabase organization/project, Vercel team/project, domain registrar, Cloudflare Turnstile widget and SMTP provider. Keep account recovery under school control and enable account MFA. Do not send passwords or service-role keys through chat.

## 2. Supabase database

1. Create/select a project in your organization. Keep its database password securely.
2. Apply migrations in filename order to an empty project using the Supabase SQL editor, or link the Supabase CLI and run `supabase db push` from this directory. The migration creates tables, RLS policies, validation triggers and storage buckets. Do not rerun the same migration manually.
3. Check the Supabase Security Advisor. Keep the `private` schema out of exposed API schemas. Do not disable RLS to work around an error.
4. In Auth settings, disable public signups, keep email/password enabled, set the minimum password length to at least 12, configure your own SMTP, and set the Site URL to your actual frontend origin.
5. Add exact redirect URLs for `https://YOUR-DOMAIN/admin/reset-password` and any staging/local origin used for testing. Local defaults must match the actual printed Vite address (`localhost` and `127.0.0.1` are different origins).

Only the `display_name` column is user-editable on the admin membership table. An authenticated user cannot grant themselves a role.

## 3. Frontend environment

Copy `.env.example` to ignored `.env` locally. In Vercel set the same frontend environment values in the project settings. Redeploy when they change: Vite embeds these at build time.

| Variable                        | Value                                         | Secret?                    |
| ------------------------------- | --------------------------------------------- | -------------------------- |
| `VITE_SUPABASE_URL`             | Your project HTTPS URL                        | No                         |
| `VITE_SUPABASE_PUBLISHABLE_KEY` | Supabase publishable key (or legacy anon key) | No; security relies on RLS |
| `VITE_TURNSTILE_SITE_KEY`       | Turnstile widget public site key              | No                         |
| `VITE_SITE_URL`                 | Exact final frontend origin                   | No                         |

`VITE_SITE_URL` generates sitemap/robots URLs at build time; do not put a path or localhost here for a production build. Initial placeholders must be replaced before release. Schools with different branding can change logo, hero image, names and text in the dashboard.

## 4. Public forms and uploads

Deploy both Edge Functions from your linked Supabase project:

```text
supabase functions deploy public-api --no-verify-jwt
supabase functions deploy upload --no-verify-jwt
```

The public API intentionally accepts anonymous requests. The upload function validates the bearer token and calls `is_admin()` itself, so disabling gateway JWT verification does not remove its administrator check. Do not remove those checks.

Configure these **server-side Supabase Edge Function secrets**, through your project's secret manager or a secure local CLI workflow:

| Secret                 | Purpose                                                         |
| ---------------------- | --------------------------------------------------------------- |
| `TURNSTILE_SECRET_KEY` | Server verification of CAPTCHA tokens                           |
| `TURNSTILE_HOSTNAMES`  | Comma-separated exact allowed hostnames, without scheme/port    |
| `ALLOWED_ORIGINS`      | Comma-separated exact origins with scheme and port where needed |
| `RATE_LIMIT_SALT`      | Random strong secret for request-key hashing                    |

Supabase provides `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY` and `SUPABASE_ANON_KEY` inside Edge Functions. These server secrets never belong in the frontend. On a self-hosted runtime supply them securely. For production use your real Turnstile keys and hostname restrictions; Cloudflare's documented test keys are only for staging tests. No CAPTCHA bypass mode is in this application.

All public operations share a limit of 20 requests per forwarded IP per hour. A shared school/mobile-network IP may encounter this limit. Tune it after staging/load testing; the platform must supply a trustworthy `x-forwarded-for` header. Do not expose the function behind a proxy that trusts a spoofed client header.

## 5. Create the first Super Admin

No password is generated by the source. Two owner-controlled setup methods are supported:

**Dashboard method:** Invite your chosen email from Supabase Authentication. Copy that invited user's UUID and, in the SQL editor, run this once after replacing the placeholder:

```sql
insert into public.admins(user_id, display_name)
values ('REPLACE-WITH-YOUR-INVITED-AUTH-USER-UUID', 'School administrator');
```

Make sure the invitation points to `/admin/reset-password`. Open the invitation email yourself, choose a strong password (at least 12 characters), then open `/admin/login`. You must own the invited mailbox. Configure and test SMTP before relying on email recovery.

**Local script method:** The owner supplies `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, `ADMIN_EMAIL`, and `SITE_URL` to a secure local process environment, then runs:

```text
node scripts/bootstrap-admin.mjs
```

The script refuses if an administrator already exists, invites the email and assigns the sole admin membership. It never prints a secret or creates a password. Clear the process environment afterwards. Invitation delivery and callback must be verified with your real provider. If the Auth user already exists, use the Dashboard method and their existing UUID instead of creating a second identity.

If the invite reaches Auth but role creation fails, check the `admins` table in the SQL editor; assign the intended UUID only after verifying there is no existing admin. Do not disable the single-admin constraint.

## 6. GitHub and Vercel

Create a private repository in your own GitHub account. This project currently sits inside an existing local Git workspace; use that repository or copy the project folder to your own clean checkout. Review `.gitignore` and staged files before pushing. Never include `.env`, secrets or real student exports in source control.

Import your repository into your Vercel account. For the selected `mr-akibbhai/School_Management_System` repository, the application is at the repository root: leave **Root Directory** at its default. Choose Vite, Build Command `npm run build`, Output Directory `dist`, Install Command `npm ci`, and a supported current Node version (22.12+). Add the frontend variables above. `vercel.json` provides SPA routing and response security headers. Deploy first to a staging URL, add that exact origin to Supabase/Turnstile settings, and execute the acceptance checklist.

Verify the returned deployment URL by opening the home page and a direct nested URL such as `/notices`. Then test admin login, save/reload/publish, forms, uploads, private result lookup and password recovery. A successful frontend build does not verify the backend. Do not open admissions until these tests pass.

## 7. Domain

In your Vercel project's Domains settings, add the domain you already own. Apply the exact DNS values Vercel currently supplies at your registrar/DNS host. Wait for DNS and TLS validation, choose the canonical domain, update `VITE_SITE_URL`, Supabase Site URL/redirect allowlist, function allowed origins and Turnstile hostnames, and rebuild/redeploy. Test apex and `www` redirects, HTTPS and recovery email links. No domain or plan has been purchased.

## 8. Costs and service limits

Checked against official documentation on 22 November 2026; check again before activation or any purchase.

- Supabase Free currently includes a 500 MB database, 1 GB file storage and 5 GB egress; free projects may pause after a week of inactivity and automatic database backups are not included. Pro starts at USD 25/month with usage/add-on charges possible. Video uploads can exhaust free storage quickly. [Supabase pricing](https://supabase.com/pricing).
- Review your eligibility, commercial-use conditions and current resource limits before selecting Vercel Hobby for a private school's production site. Do not assume the free plan fits school operations. [Vercel Hobby documentation](https://vercel.com/docs/plans/hobby), [Vercel plans](https://vercel.com/pricing).
- Domain registration renewals, production SMTP, database backups and storage/traffic overages may cost extra. Account owners choose and approve any paid service.

Official references: [Vite on Vercel](https://vercel.com/docs/frameworks/frontend/vite), [Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security), [password recovery](https://supabase.com/docs/guides/auth/passwords).
